Open WebUI: "alembic.util.exc.CommandError: Can't locate revision identified by '…'"

By MV2 of Munim, Inc., with AI agents. Checked on 9 November 2026 against every Open WebUI release tag from v0.3.17 to v0.13.3 (8 November 2026), the newest release then.

Open WebUI stops at startup, often in a restart loop, and its log shows Error running migrations: Can't locate revision identified by '…' followed by alembic.util.exc.CommandError: Can't locate revision identified by '…' with a 12-character id.

Short answer: the id is the last database migration your Open WebUI data has been through. A newer Open WebUI release applied it, and the release you are starting now is older, so it doesn't know that id and refuses to start. Find your id below to see which release first shipped it, then run that release or any newer one (the newest on 9 November 2026 was v0.13.3). Open WebUI's migrations only go forward, so you can't go back to an older release on the same data. Going back means restoring a backup taken before the upgrade.

Why it happens

Open WebUI records the newest migration it has applied in the alembic_version table of its database. Each time it starts, it runs command.upgrade(alembic_cfg, 'head') (its run_migrations() in config.py; ENABLE_DB_MIGRATIONS is on unless you set it to false). Alembic first looks up the recorded id among the migrations that release ships. If the id is from a newer release, it isn't there, and Alembic stops with this error. Open WebUI never runs a downgrade.

It usually shows up after one of these:

  • a rollback to an older image after an upgrade (by hand, a helm rollback, or an automatic rollback after a failed health check while migrations were running),
  • a floating tag such as :main or :ollama that resolved to an older build than the one that last ran on this data,
  • two Open WebUI instances of different versions sharing one database,
  • a :dev build, which can carry migrations that no release has yet.

Ids reported in public threads

  • 9f6c2a8d1b43 (rolling back from the 0.13.1 / 0.13.2 :ollama image, whose amd64 build had no Ollama, issue #33942): first shipped in v0.13.1, so the database had been migrated by v0.13.1 or newer.
  • 3e0e00844bb0 (reported in a thread about a failed start, issue #19797): first shipped in v0.6.41, so the database had been migrated by v0.6.41 or newer.
  • 9f0c9cd09105 (after switching between versions, discussion #13789): first shipped in v0.6.6, so the database had been migrated by v0.6.6 or newer.

If you rolled back because the :ollama image had no Ollama

On 8 November 2026 an Open WebUI maintainer confirmed in #33942 that the amd64 :ollama images for 0.13.1 and 0.13.2 were built without Ollama, and that rolling back to 0.13.0 does not work because 0.13.1 added a database migration (9f6c2a8d1b43, the id in the error). On 9 November the maintainer added that the 0.13.3 :ollama image (amd64 and arm64) ships Ollama again. So the fix is to go forward, not back: pull the :ollama image again so you get 0.13.3 or newer, and start it on the same volume.

Find your id

From the log (change open-webui to your container name):

docker logs open-webui 2>&1 | grep "locate revision"

Or read it straight from the database while Open WebUI is stopped. With the default SQLite database in the official Docker image (the volume mounted at /app/backend/data), using a throwaway Python container (change open-webui to your volume name from docker volume ls, or to the host folder you mounted):

docker run --rm -v open-webui:/data python:3.12-slim python3 -c "import sqlite3; print(sqlite3.connect('/data/webui.db').execute('select version_num from alembic_version').fetchall())"

With PostgreSQL (DATABASE_URL starts with postgresql://), run SELECT version_num FROM alembic_version; in that database (in the schema named by DATABASE_SCHEMA, if you set it).

Fix it

  1. Look up the id in the table. The release in its row is the oldest one that can start on your data.
  2. Run that release or newer. With Docker, pin the tag, for example docker pull ghcr.io/open-webui/open-webui:v0.13.3, then start the container again with the same options and volume you used before, changing only the image tag. With Docker Compose, set image: ghcr.io/open-webui/open-webui:v0.13.3 and run docker compose up -d. With pip, pip install "open-webui==0.13.3". A pinned tag keeps a floating tag from moving you back again.
  3. If you really need the older release (say a newer one has a bug that blocks you), stop Open WebUI and restore the copy of your data volume or webui.db (or your PostgreSQL dump) taken before the upgrade, then start the older release on it. Anything created after that backup is lost. If you have no such backup, stay on the newer release and wait for a fix.

Don't edit alembic_version to an older id ("stamping"), and don't set ENABLE_DB_MIGRATIONS=false to force the old release to start. Either way the tables keep the newer layout that the old code doesn't expect, and the next upgrade tries to apply migrations whose changes are already there. Before any upgrade, copy the data volume (or dump the database) first; the 0.13.1 release notes recommend backing up the database and all associated data before upgrading in production.

How this was made, and its limits

AI agents working for MV2 of Munim, Inc. listed backend/open_webui/migrations/versions at every release tag (vX.Y.Z) of the Open WebUI git repository, read each migration's own revision and down_revision, and took the first tag that contains it. Dates are GitHub release dates. The mapping is by git tag. A floating image tag (:main, :ollama, :cuda) can point at a build between releases, so it can hold migrations that the next release ships, and a :dev build can hold migrations that are not in this table yet. Helm chart versions are not Open WebUI versions: check the chart's appVersion. Corrections are welcome as issues at github.com/munimtechnologies/local-ai-checkup.
