Self-hosted Dify: which advisories affect my version?

By MV2 of Munim, Inc., with AI agents. Checked against Dify's own security advisories on 11 October 2026 and again on 12 October 2026 (no new ones); every row links its source.

Dify runs from Docker images (langgenius/dify-api, langgenius/dify-web), not from a package you install, so npm audit, pip-audit and Dependabot never check Dify's own version. Image scanners such as Trivy look at the operating system and libraries inside the image, not at Dify's advisories. Its CVEs reach OSV.dev only as git-commit ranges, and three 2026 advisories have no CVE ID at all. So the reliable check is to compare your version with Dify's advisory list, which this page does.

The latest stable release is 1.17.1 (10 September 2026); 2.0.0 is in beta. Anything older than 1.16.0 is affected by at least one 2026 advisory:

  • Before 1.16.0: any signed-in workspace member can change or disable another app's MCP server (CVE-2026-105761, CVSS 7.1).
  • Before 1.14.2: any signed-in console user who knows a file ID can read the text of documents uploaded in another workspace through the file preview (GHSA-9c9q-5rj5-mjj2, CVSS 7.7, no CVE ID). This matters when one Dify instance hosts several teams or customers.
  • Before 1.14.0: another workspace's External API details can be read and its usage enumerated (GHSA-5vmp-5q9h-hmr7, High; GHSA-fj5w-7rc8-3f3f, Medium; no CVE IDs).
  • Before 1.13.0: unauthenticated server-side request forgery through /console/api/remote-files/upload (CVE-2026-105762, High). On a cloud VM that can reach internal services or the metadata endpoint.
  • Before 1.11.0: the model provider configuration endpoint returns your provider API keys in plain text (CVE-2025-67732, High).

Find it under your avatar, then About, or run docker compose images in dify/docker and read the langgenius/dify-api tag. The check runs in your browser.

What to do

  1. Update to 1.17.1, the latest stable release. Its notes also list security hardening without advisories, such as agent skill traffic that ignored the SSRF private-network allowlist. Back up the docker/volumes folder and your .env first, then follow Dify's upgrade guide for Docker Compose.
  2. If you were on 1.10.x or older and the console was reachable by others, rotate the model provider API keys stored in Dify.
  3. If one instance serves several teams or customers, treat anything before 1.14.2 as having let users read other workspaces' documents and External API settings.
  4. Check what's exposed. Dify's Docker Compose setup publishes nginx on ports 80 and 443 on all addresses by default (EXPOSE_NGINX_PORT, EXPOSE_NGINX_SSL_PORT). If only you use it, bind it to 127.0.0.1 or a VPN address, and turn off open sign-up.
  5. Check your .env, not just your version. Upgrades keep it as it was. Installs from before 1.15.0 may still use the SECRET_KEY published in .env.example. The plugin debugging port 5003 is also published on all addresses. The Dify hardening checklist covers both, plus INIT_PASSWORD, CORS and the default service passwords.
