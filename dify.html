Self-hosted Dify: which advisories affect my version?

By MV2 of Munim, Inc., with AI agents. Checked against Dify's own security advisories and release notes on 15 November 2026 (earlier checks: 11 and 12 October 2026). The 14 November advisory was also read in Dify's source at the 1.17.1 and 1.18.0 tags. We did not test it on a running Dify.

15 November 2026: 1.17.1 is no longer safe. Earlier versions of this page told you to update to 1.17.1. On 14 November Dify published GHSA-6j8g-rp8v-55vr (Medium, CVSS 6.5, no CVE ID), which affects 1.17.1 and every earlier version and is fixed in 1.18.0 (23 October). The newest release is 1.19.0 (4 November). When we checked on 15 November, the advisory was not in OSV.dev or the GitHub Advisory Database, so scanners that read those won't show it. The CVE checker on the home page doesn't list it yet either. Until it does, treat any Dify at 1.17.1 or older as affected.

Dify ships as Docker images (langgenius/dify-api, langgenius/dify-web), not as a package you install, so npm audit, pip-audit and Dependabot never check Dify's own version. Image scanners such as Trivy look at the operating system and libraries inside the image, not at Dify's advisories. On OSV.dev, Dify's CVEs appear only as git-commit ranges, and five of the advisories below, the newest included, have no CVE ID at all. To know whether your Dify is affected, compare your version with Dify's own advisory list, below.

  • 1.17.1 and earlier: anyone can get around every per-IP rate limit, including the one on password-reset emails (GHSA-6j8g-rp8v-55vr, below).
  • Before 1.16.0: any signed-in workspace member can change or disable another app's MCP server (CVE-2026-105761).
  • 1.13.3 and earlier: signed-in users can read other workspaces' uploaded documents and External API settings (three advisories, no CVE IDs).
  • Before 1.13.0: unauthenticated server-side request forgery through remote file upload (CVE-2026-105762).
(runs in your browser on the home page; until it lists the 14 November advisory, add it yourself for 1.17.1 or older)

To find your version on a Docker Compose install, run docker compose images api in Dify's docker folder and read the tag.

The 14 November advisory: per-IP rate limits can be dodged (1.17.1 and earlier)

Dify's per-IP rate limiters, such as EMAIL_SEND_IP_LIMIT_PER_MINUTE (default 50 a minute), use the caller's IP address as the bucket. In 1.17.1, extract_remote_ip() in api/libs/helper.py takes that address from the CF-Connecting-IP header if it is present, then from the first X-Forwarded-For value, and only then from the real connection address. A client can set both headers to anything, so every request can claim a new address and land in a fresh bucket. The advisory says this lets an attacker send password-reset emails in bulk and hide where requests come from. It does not by itself allow an account takeover.

The default Docker Compose setup is affected too. In 1.17.1, the bundled nginx's docker/nginx/proxy.conf.template sends X-Forwarded-For $proxy_add_x_forwarded_for, which keeps whatever the client sent and appends the real address to the end, and it passes CF-Connecting-IP through unchanged. Since the API reads the first value, the client's fake one wins.

What 1.18.0 changed: extract_remote_ip() now returns only the connection address (request.remote_addr). Forwarded headers count only through Werkzeug's ProxyFix, which is now set up with x_for=1 and switched on by RESPECT_XFORWARD_HEADERS_ENABLED. The bundled nginx now sends X-Forwarded-For $remote_addr. According to the 1.18.0 release notes, the bundled Compose turns forwarded-header handling on for the API behind nginx, while a standalone API keeps it off by default. If a load balancer or Cloudflare sits in front of nginx, you have to configure trusted real-IP handling there, or all your visitors may share the proxy's rate-limit bucket.

What to do

  1. Update to 1.18.0 or newer, ideally 1.19.0. 1.18.0 is a big upgrade. Read its upgrade guide first: back up the database, vector data, files and env files; upgrade the API, worker, web, Agent Backend and sandbox images together; set the Local sandbox token before restarting (the 1.17.1 runtime image does not support the new --require-auth-token flag); and leave PASSWORD_PEPPER empty on an existing install, because setting it invalidates existing password hashes. 1.19.0 needs Docker Compose 2.35.0 or later, and its notes list more security fixes (provider-model changes limited to owners and admins, saved credentials no longer returned by configuration reads, SSRF client cookie scoping).
  2. If you must stay on 1.17.1 for now, stop the bundled nginx from passing the client's headers on. The advisory suggests this for deployments without Cloudflare. docker/nginx/proxy.conf.template is mounted into the nginx container, so change its X-Forwarded-For line and add one for CF-Connecting-IP: 
    proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header CF-Connecting-IP "";
    Then run docker compose up -d --force-recreate nginx. On 1.17.1 the API reads these headers itself, so turning on RESPECT_XFORWARD_HEADERS_ENABLED alone does not help. An upgrade or git pull may overwrite the file. Behind Cloudflare or another proxy, the change above puts all visitors in that proxy's bucket. Instead, have nginx take the real address only from the proxy's own ranges (nginx's set_real_ip_from and real_ip_header), and don't let the origin accept connections from anywhere else. We have not tested either change.
  3. If you ran 1.10.x or earlier and others could reach the console, rotate the model provider API keys stored in Dify (CVE-2025-67732).
  4. On a multi-team or multi-customer instance, assume any version before 1.14.2 let users read other workspaces' documents and External API settings.
  5. By default nginx is published on ports 80 and 443 on every address (EXPOSE_NGINX_PORT, EXPOSE_NGINX_SSL_PORT). For a single-user setup, bind it to 127.0.0.1 or a VPN address and turn off open sign-up.
  6. Audit .env, because upgrades leave it as it was: installs from before 1.15.0 may still use the published SECRET_KEY from .env.example, and the plugin debugging port 5003 is published on every address. The Dify hardening checklist covers these, plus INIT_PASSWORD, CORS and the default service passwords.
