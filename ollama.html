Ollama CVEs: is my Ollama version affected?

By MV2 of Munim, Inc., with AI agents. Checked against CERT Polska, NVD, CERT/CC, the Zero Day Initiative and the researchers' own write-ups on 12 October 2026; every row links its source.

Short answer: update to the latest Ollama release, which was 0.40.3 (11 October 2026) when this page was checked. Any version from 0.35.0 on is past every Ollama CVE that names a fixed version. The most recent one is CVE-2026-103663: an unauthenticated /api/pull request can write a file outside the model store in 0.34.2 up to 0.35.0 (CERT Polska, 8 October 2026). In most Docker images Ollama runs as root, so a planted file can run on the next restart.

Two other 2026 records name no fixed version. Neither changes the verdict for a current release, but both are another reason not to let untrusted machines reach port 11434. See below.

Find your version: run ollama --version, or open http://127.0.0.1:11434/api/version. With Docker, run docker exec <container> ollama --version. The check runs in your browser and nothing you type is sent anywhere.

Is your Ollama reachable from other machines?

That decides how much these CVEs matter. Ollama's API has no login. Anyone who can reach port 11434 can pull, create and delete models, and the CVEs below need nothing more than that.

  • Linux: ss -tlnp | grep 11434. 127.0.0.1:11434 is local only. 0.0.0.0:11434 or *:11434 means other machines can connect, usually because OLLAMA_HOST=0.0.0.0 is set.
  • Windows: netstat -ano | findstr :11434. macOS: lsof -nP -iTCP:11434 -sTCP:LISTEN.
  • Docker: -p 11434:11434 publishes on every interface, and on Linux it skips ufw and firewalld. Use -p 127.0.0.1:11434:11434 unless other machines need it.
  • If other machines do need it (Open WebUI on another host, a team server), put a reverse proxy with authentication in front, such as Caddy with basic auth or a token header, and let only that proxy reach Ollama.

Ollama CVEs that name no fixed version

  • CVE-2026-5757 (CVSS 7.5, CERT/CC VU#518910, 22 April 2026): an unauthenticated heap memory disclosure through the model quantization engine, triggered by a crafted GGUF file, with the data sent out through the registry push API. CERT/CC wrote that it couldn't reach Ollama and that no patch was available. NVD lists versions up to 0.13.5 and names no fix. MV2's reading: the code path and the way data leaves (quantizing through /api/create, then /api/push) match Bleeding Llama, CVE-2026-7482, which Cyera reports as fixed in 0.17.1. That suggests they're the same bug, but neither CERT/CC nor NVD says so, and MV2 hasn't confirmed it. Whatever version you run, don't let untrusted machines reach /api/create.
  • CVE-2026-15685 (ZDI-26-403, CVSS 7.5, published as a 0-day on 8 July 2026): an unauthenticated request can crash Ollama through the downloadBlob function. ZDI reported it in May 2025 and recorded no vendor response. NVD lists only 0.7.1, and nobody has published a fixed version or said whether later versions are affected. The only mitigation ZDI gives is to restrict who can reach the server.

The site's version checker doesn't list these two. The only versions their records name (up to 0.13.5, and 0.7.1) are already flagged by the CVEs in the table above. For a current release, what matters is the listening address above.

If an affected version was reachable

  1. Update to the latest release. With Docker, pull ollama/ollama:latest (or a pinned tag) and recreate the container, rather than updating inside it.
  2. After CVE-2026-103663 (0.34.2 to 0.34.x reachable by others), look for files you didn't put in the model store and, in Docker, in /usr/lib/ollama. Rebuild the container from a fresh image.
  3. After Bleeding Llama (before 0.17.1 reachable by others), rotate API keys and tokens that were in Ollama's environment, and assume prompts sent to it may have leaked.
  4. Close the port as described above, then run ollama list and remove models you don't recognise.
