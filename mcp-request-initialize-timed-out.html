MCP: "Request 'initialize' timed out"

By MV2 of Munim, Inc., with AI agents. Written on 12 November 2026 from the source of the MCP Python SDK (v2.3.0 and v1.27.2), the MCP TypeScript SDK (v2.4.0 and 1.32.2), the OpenAI Agents SDK (main branch that day), Pydantic AI v2.68.0 and Open WebUI v0.13.3. Nothing was run; see limits.

Your agent or chat app starts an MCP server and fails before any tool is listed:

mcp.shared.exceptions.MCPError: Request 'initialize' timed out

The client sent the MCP handshake and the server did not answer in time. Almost always the server is slow to start, not broken: npx or uvx downloading the package on first launch, a Python server importing heavy libraries, a server that logs in somewhere before it answers, or a busy CI runner. The fix is to give the handshake more time in your client's setting, and the setting, its name and its default differ a lot between clients. That is what this page lists.

The setting and its default, client by client

Client (version read)Setting that bounds the handshakeDefaultAlso applies to
MCP Python SDK 2.x, ClientSession or Client (v2.3.0)read_timeout_seconds (float, seconds)None: no timeout at allEvery later request that doesn't pass its own timeout, including call_tool (its read_timeout_seconds defaults to the session's). See also the 10-second probe.
MCP Python SDK 1.x, ClientSession (v1.27.2)read_timeout_seconds (a datetime.timedelta)None: no timeoutSame: a per-request value wins, otherwise the session value is used.
MCP TypeScript SDK 1.x / 2.x (1.32.2, v2.4.0)client.connect(transport, { timeout }) in milliseconds; in 1.32.2 connect() passes these options to the initialize requestDEFAULT_REQUEST_TIMEOUT_MSEC = 60,000 (60 s), per requestEach request takes its own timeout; resetTimeoutOnProgress (default false) and maxTotalTimeout (default none) exist for long tool calls.
OpenAI Agents SDK, MCPServerStdio, MCPServerSse, MCPServerStreamableHttp (main, 12 Nov 2026)client_session_timeout_seconds5 seconds in all three classesIt is passed to the SDK as the session read timeout (a timedelta with mcp 1.x, a float with mcp 2.x), so with the Python SDK rules above it is also the default for later requests. None or 0 turns it off. Per openai-agents-python#5405, the stock stdio example can fail with Request 'initialize' timed out on a cold start.
Pydantic AI, MCPToolset (v2.68.0)init_timeout: "Timeout in seconds for the initial connection and initialize handshake"5 secondsSeparate from read_timeout (default 300 s) for the long-lived connection. Both go to the FastMCP Client; if you pass your own pre-built FastMCP client, set them on that client instead (Pydantic AI raises an error if you pass either together with one). We did not read FastMCP's own timeout message.
Open WebUI (v0.13.3)Environment variable MCP_INITIALIZE_TIMEOUT10 secondsPassed as the SDK client's read_timeout_seconds, so it bounds the handshake and listing tools. Tool calls use AIOHTTP_CLIENT_TIMEOUT_TOOL_SERVER instead (no timeout when unset; utils/mcp/client.py).

The MCP Python SDK itself has no handshake timeout. When a Python client gives up after 5 or 10 seconds, that number comes from the framework or app on top of it, so that is where to raise it.

What to do

  1. Time the server's start on its own. Run the exact command from your config in a terminal and see how long it takes to print anything or settle, and whether it fails outright (a missing package, a registry it can't reach, an API key it wants). A server that never starts gives the same timeout as a slow one.
  2. Remove the download from the start. npx -y some-server and uvx some-server may fetch the package on first run or after a cache clean, and that counts against the handshake. Installing it once (npm install -g, uv tool install) and pointing the config at the installed command takes that out.
  3. Raise the right setting from the table, for example client_session_timeout_seconds=30 (OpenAI Agents SDK), init_timeout=30 (Pydantic AI), MCP_INITIALIZE_TIMEOUT=60 (Open WebUI, then restart it). Wrapping the connect in your own asyncio.timeout(60) does not help: an outer timeout can only cut a wait shorter, never extend the session's own read timeout.
  4. Watch what the bigger number also changes. With the Python SDK, the session read timeout is also the default for tool calls. A small value set for the handshake can cut off slow tools; a large one lets a hung tool hold the agent that long. Where the client lets you, give tool calls their own per-call timeout. Pydantic AI and Open WebUI already keep the two apart.

MCP Python SDK 2.x: a fixed 10-second probe before initialize

From reading mcp v2.3.0: Client defaults to mode="auto", which first sends a server/discover probe (for servers on the newer protocol) and falls back to the classic initialize handshake on older servers. In mcp/client/session.py the probe uses a fixed DISCOVER_TIMEOUT_SECONDS = 10.0, not your read_timeout_seconds. In mcp/client/_probe.py, any MCPError from the probe, a timeout included, leads to the fallback, except a -32022 answer whose supported list shares no handshake-era version. So with a slow-starting older server, the first 10 seconds go to a probe you can't configure, and then initialize gets your timeout. The error you finally see names 'initialize'. If you need the old single handshake, Client(..., mode="legacy") "forces the initialize handshake" (its docstring). We did not check which mode each framework uses.
