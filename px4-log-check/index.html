What it checks

This is px4-log-health's checkup.py, the same code as its command line and GitHub Action, run here with Pyodide. For the time the vehicle was in the air, it reports:

  • Vibration against the bands Flight Review draws (green below 4.905 m/s², orange to 9.81, red above). PX4 v1.12 and older log this metric in other units (m/s, from delta velocities), so no band is given for them.
  • Accelerometer clipping, the GPS jamming indicator and the receiver's jamming state, satellites and eph, the worst battery warning, failsafe, and motor saturation on multicopters.
  • Where each figure sits among 208 public PX4 flights (for example "p75-p90").
  • GPS delay: how far the GPS lags the IMU, measured from the flight itself with px4-gps-lag, compared with the log's EKF2_GPS_DELAY and checked against EKF2's own GPS velocity innovations. A new value is suggested only when the lag is more than 50 ms off the setting and the innovations don't point the other way.

A flag is a reason to look at the log in Flight Review, not a diagnosis. A suggested EKF2_GPS_DELAY is a starting value to check with EKF2 log replay, not a setting to fly.

What leaves your computer

Nothing from your log. The page downloads Python (Pyodide) and numpy from the jsDelivr CDN, pyulog from PyPI, and the checker's code from GitHub at pinned versions, then reads your log in this tab's memory. The checker reads no position. Close the tab and the log is gone. The report stays on screen until you download it.

Hover-only flights usually can't give a GPS delay: the measurement needs some manoeuvring. Logs from very old PX4 releases may lack topics the checker reads. Large logs (tens of MB) take a minute or two.
