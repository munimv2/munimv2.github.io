Open WebUI: "TypeError: crypto.randomUUID is not a function" over plain HTTP

By MV2 of Munim, Inc., with AI agents. Checked on 9 November 2026 against all 85 Open WebUI release tags from v0.6.0 to v0.13.3 (the newest release then).

You open Open WebUI at a plain-HTTP address such as http://192.168.1.20:8080 or a Docker host name, and something stops working: the chat page stays on a spinner and no chat opens (0.13.1), or the skill editor stays disabled (0.12.0), or a button silently does nothing. The browser console (F12) shows Uncaught TypeError: crypto.randomUUID is not a function.

Short answer: browsers only provide crypto.randomUUID() on secure pages: HTTPS, or http://localhost / 127.0.0.1. On any other plain-HTTP address it doesn't exist, and Open WebUI code that calls it throws. Update to Open WebUI 0.13.2 or newer (0.13.3 was the newest on 9 November 2026): in those releases no code that runs over plain HTTP calls it. Better still, serve Open WebUI over HTTPS, which also protects the password you type into it.

A file having a call doesn't mean every page that uses the file breaks: only the action that reaches that line fails. That is why, for example, #33919 reports that 0.13.0 loaded the chat page fine on the same setup where 0.13.1 did not.

Fix it

  1. Update Open WebUI to 0.13.2 or newer. Docker: docker pull ghcr.io/open-webui/open-webui:v0.13.3 (or your usual tag), then recreate the container with the same volume. pip: pip install -U open-webui. Back up the data volume first. Open WebUI can't be downgraded on the same data (see "Can't locate revision").
  2. Serve it over HTTPS with a reverse proxy (Caddy, nginx, Traefik) in front of port 8080. See Open WebUI behind a reverse proxy. This fixes the error on every version, and it also makes the microphone (voice input and calls) and clipboard features work, because browsers only allow those on secure pages too.
  3. Or reach it as localhost through an SSH tunnel from your own computer: ssh -L 8080:localhost:8080 you@server, then open http://localhost:8080. The browser treats localhost as secure.
  4. Stop-gap for one Chromium-based browser (Chrome, Edge): open chrome://flags/#unsafely-treat-insecure-origin-as-secure (edge://flags/… in Edge), add your exact address such as http://192.168.1.20:8080, enable it and relaunch. This affects only that browser profile, and the traffic is still unencrypted.

Plain HTTP on a network sends your Open WebUI password, session token and every chat in clear text to anyone on the same network. Updating fixes the error. Only HTTPS (or the SSH tunnel) fixes the exposure.

What about the calls still in 0.13.3?

From v0.12.3 to v0.13.3, src/lib/encryption/client.ts has three crypto.randomUUID() calls (lines 267, 422 and 440 in v0.13.3). We read that file at v0.13.3. The session setup throws at once if window.isSecureContext is false (line 162), and all three calls are only reached once a session is active, so over plain HTTP that code stops before reaching them. In other words, that feature needs a secure page, by design. We read the code; we did not run it in a browser.
