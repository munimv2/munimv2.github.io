LiteLLM proxy: am I affected?

By MV2 of Munim, Inc., with AI agents. Checked against LiteLLM's own security advisories and the GitHub Advisory Database on 12 October 2026; the CVE-2026-84377 row was corrected on 13 October 2026 to OSV's per-release-line ranges. Every row links its source.

A LiteLLM proxy usually holds the keys to every model provider you use, so its bugs are worth checking. The newest two have no CVE ID, and OSV.dev had no record of them on 11 October 2026, so dependency scanners that read OSV won't report them:

  • 1.91.0 up to 1.100.4, and 1.101.0-1.101.2, 1.102.0-1.102.1 and 1.103.0: GHSA-7hp6-4w63-5g45 (CVSS 9.9, 30 September 2026). The proxy uses one key both to seal secrets and to mint session tokens, so any user with the internal_user role can forge an admin session, become proxy admin and run commands on the host through the MCP stdio endpoint. It works in the default configuration from 1.91.0; 1.87.0-1.90.x are affected only with EXPERIMENTAL_UI_LOGIN=true.
  • Before 1.95.0: GHSA-g5ff-637f-6q2m (CVSS 8.1, 1 October 2026). A user with only the internal_user_viewer role, which many deployments grant to anyone who signs in with SSO, can read any file the proxy can, such as /proc/self/environ with the master key and provider keys. There's no configuration workaround.
  • Before 1.84.0: CVE-2026-49468 (CVSS 9.8). A crafted Host header can get an unauthenticated request onto protected management routes. Proxies behind a CDN, WAF or reverse proxy that validates the Host header are mostly not affected.
  • Exactly 1.82.7 or 1.82.8: these PyPI releases were malicious (March 2026). They harvested credentials and files and sent them to a remote server. If either was ever installed, assume every credential that environment could see was exposed.

Run pip show litellm, or open http://127.0.0.1:4000/health/readiness and read litellm_version. For Docker, the image tag usually carries the version. The check runs in your browser.

What to do

  1. Update to 1.104.0 or newer (the latest release, 1.105.0, is best). If you must stay on a release line, the privilege escalation is fixed in 1.100.4, 1.101.3, 1.102.2 and 1.103.1, and the file read needs at least 1.95.0.
  2. If you can't update today, set EXPERIMENTAL_UI_LOGIN=false. It closes the privilege escalation path, but it also breaks CLI SSO and Claude Code gateway login. Nothing short of updating closes the viewer-role file read, so remove viewer accounts you don't need.
  3. If internal or viewer users you don't fully trust could reach an affected version, rotate the master key and every provider key the proxy holds, and check the admin list and the MCP server settings for entries you didn't make.
  4. Check your install history for 1.82.7 and 1.82.8. Look in pip logs, lock files, CI logs and image build logs from March 2026. If either shows up, rotate every provider key, the master key and any cloud credentials on that machine or in that CI job.
  5. Keep the admin UI and management routes private. Only the routes your apps call need to be reachable. The LiteLLM hardening checklist covers the master key, LITELLM_SALT_KEY, turning off the master-key UI login, stdio MCP servers, and Caddy and nginx configs that keep /ui on your own network.
