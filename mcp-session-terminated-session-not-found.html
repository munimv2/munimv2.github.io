MCP "Session terminated" / 404 "Session not found" after an idle break or a server restart

By MV2 of Munim, Inc., with AI agents. Written on 12 November 2026 from the source of the MCP Python SDK (v1.29.1, v1.30.0, v2.0.0 to v2.3.0), the TypeScript SDK (1.32.2 and main), the Rust SDK (main), Open WebUI v0.13.3 and the issues linked below. Read from the source, not run. See the limits.

An MCP client on the Streamable HTTP transport works, then every call fails with one of these:

mcp.shared.exceptions.McpError: Session terminated
Streamable HTTP error: Error POSTing to endpoint: {... "Session not found" ...}
MCP error -32001: Request timed out
HTTP 404 Not Found: Session not found

They are all the same event. The server no longer knows the client's Mcp-Session-Id and answers HTTP 404, as the MCP spec tells it to. The spec then says the client must start a new session (2025-11-25 transports, Session Management, rule 4). The official SDKs leave that step to the application, and many applications don't take it, so the old session ID is sent again and every call fails until the client is restarted.

Why the server forgot the session

CauseHow to recognise it
Idle expiry, new default since 7 September 2026. Python MCP SDK servers on mcp 2.2.0+ or 1.30.0+ close a stateful session that has had nothing in flight for 30 minutes (DEFAULT_SESSION_IDLE_TIMEOUT: Final = 30 * 60). Up to v2.1.1 and v1.29.1 the default was None, no expiry. Per the v2.2.0 release notes (PR #3395; #3426 on 1.x), clients that keep the GET stream open, such as the SDK's own Client, aren't affected.The first call after a gap of 30 minutes or more fails, and the reconnect or retry works. On v2.3.0 the server logs Session <id> idle timeout, then Rejected request with unknown or expired session ID: <id> (INFO).
Idle expiry in the Rust SDK (rmcp). LocalSessionManager's SessionConfig::keep_alive "Defaults to 5 minutes" (DEFAULT_KEEP_ALIVE = Duration::from_secs(300) on main, 12 November 2026). Per rust-sdk#689, older rmcp answered an unknown session with 401 instead of 404.Same pattern, after a 5-minute gap. This is the case in claude-code#83404 (rmcp 2.2.0 server).
Server restart or redeploy. The Python and TypeScript SDKs keep sessions in memory, so a restart forgets all of them.Every client fails at once, right after a deploy, a container restart or a crash.
Several replicas behind a load balancer. The session lives on one replica, and the next request lands on another (per higress#4788).Intermittent 404s from the first minutes of a session, with no idle gap.
The session was deleted (the client or a proxy sent DELETE).Fails after a tab, chat or proxy connection was closed.

The TypeScript SDK server (1.32.2) has no idle timeout. Its sessions end only on DELETE or close(). If you see this error against a TypeScript server, look at restarts and load balancing first.

Not this error: a 404 on the first request, before any session exists, means a wrong URL (often /mcp vs /mcp/, or a missing path). The Python client then says Not Found, not Session terminated: it only uses "Session terminated" when it already holds a session ID.

"-32001: Request timed out" can hide a 404. In the TypeScript SDK, -32001 is ErrorCode.RequestTimeout, and it is also the code the TypeScript SDK server puts on its own Session not found answer. If a "timeout" comes back in milliseconds, and always after an idle gap, check the server log for a 404 before raising any timeout (see the initialize-timeout page for real timeouts).

Fixes on the server

  1. Make the idle window longer than your users' gaps. Python mcp 2.2.0+: mcp.run(transport="streamable-http", session_idle_timeout=4 * 3600) (also on streamable_http_app() and run_streamable_http_async()). mcp 1.30.0: FastMCP(..., session_idle_timeout=...). rmcp: set keep_alive on the SessionConfig of your LocalSessionManager.
  2. Turning expiry off (session_idle_timeout=None) brings back the old behaviour, but sessions that are abandoned without a DELETE then stay until restart. With the SDK's 10,000-session cap still on, that ends in the 503 Too many open sessions of fastmcp#5210. Set both or neither: the release notes' way to turn both off is session_idle_timeout=None, max_sessions=None. A long timeout is usually the better choice.
  3. Go stateless if the server never needs to send requests to the client (sampling, elicitation). A stateless server issues no session ID, so there is nothing to expire, lose on restart or route to the wrong replica. In the Python SDK's stateless mode, server-to-client requests raise NoBackChannelError; notifications still work. In rmcp, one project did it with NeverSessionManager and stateful_mode = false (openab#1578).
  4. Several replicas: route by the Mcp-Session-Id header (sticky sessions), or go stateless.
  5. Restarts always drop in-memory sessions. Only clients that re-initialize recover, so check the table above for the clients your users run.

Fixes in a client you write

Do what the spec says: on a 404 to a request that carried a session ID, drop the session, send a fresh initialize without the old ID, and then decide whether to retry.

  • Python SDK: catch the error whose message is Session terminated (the code is -32600 on 2.x and 32600 on 1.30.0), then close the whole client and transport and open a new one. Reusing the transport resends the stale ID, because it never clears session_id.
  • TypeScript SDK 1.x: catch StreamableHTTPError with code === 404 after a session exists, then create a new transport and client and connect again.
  • Retry once at most. Under the spec, the server answers 404 instead of running the request, so the call wasn't carried out (claude-code#83404: the write "was in fact never executed"). Hermes and Claude Code retry the call; mcp-proxy chose to recover the session "without replaying operations". If a 404 might come from something other than the MCP server (a proxy or gateway), don't blindly replay writes.
  • Avoid the idle window: per the v2.2.0 release notes, a client that keeps the GET stream open isn't expired by Python servers. That doesn't help with restarts.
