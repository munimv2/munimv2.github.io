Ollama pull "Error: 403:" behind a company proxy, and the four other errors the same block prints

By MV2 of Munim, Inc., with AI agents. Tested on 12 November 2026: the official Ollama v0.40.16 Linux release binary pulled a tiny model from a local stand-in registry that answered one kind of request with HTTP 403 and a block page, the way a filtering company proxy does. Read the limits before relying on it.

A web filter or proxy that refuses one of the requests ollama pull makes doesn't always produce an error with "403" in it. In our test, the same 403 block page gave five different results, depending on which request it hit. Two of them never mention 403 at all, and in three the server log (even with OLLAMA_DEBUG=1) has no line with the 403 in it either. Retrying doesn't help: a 403 is a policy decision, and it gives the same answer every time.

The HTTP API answered each of these with status 500 and the same text in {"error": "…"}, so Open WebUI and other front ends that call /api/pull should show the same messages. In a control run with nothing blocked and blobs redirected to a second host, the way Ollama's own registry works, the pull succeeded.

Why the messages differ (Ollama v0.40.16 source)

  • Manifest, token and HEAD go through makeRequestWithRetry in server/images.go. For any status of 400 or more except 401 and 404, it returns "<status>: <response body>". On a 401 it fetches a token (server/auth.go), which reports a failed token request in the same format. The manifest path adds pull model manifest: in front. A HEAD response has no body, so its error is just 403: . The function logs only network failures (request failed: …), not HTTP error statuses, which is why the log stays silent.
  • The registry blob GET runs in a loop with a 30-second timeout in server/download.go (blobDownload.run). Each 403 is logged as failed to get direct URL; backing off and retrying and retried. When the 30 seconds are up, you get Go's context deadline exceeded, and the 403 is gone from the message.
  • The download host is fetched in downloadChunk, which doesn't check the HTTP status. It copies the response body as if it were the file's bytes. A block page is far shorter than a download part (at least 100 MB, or the whole blob if that is smaller), so the copy runs out early with EOF. That is retried 6 times (maxRetries = 6), waiting 1, 2, 4, 8, 16 and 32 seconds, which gives the minute before max retries exceeded: EOF.

So "max retries exceeded: EOF" isn't always a flaky connection. Most advice for it is about dropped connections and says to run the pull again. If it fails the same way every time, and the log shows attempt 0 failed: EOF within a second or so of starting, suspect a proxy refusing the download host. A pull that resumes and makes progress between failures is the flaky-connection kind.

What this looks like in a real report

Per ollama/ollama#19604 (opened 8 November 2026, now closed): behind a corporate proxy, every pull failed with Error: 403:, while curl to the registry worked through the same proxy. The debug log ended with POST "/api/pull" and status 200, with no 403 in it. A curl -sI of the blob URL through the proxy then returned HTTP/2 403 with a 17,518-byte HTML page saying Your system policy has denied access to the requested site. That matches our HEAD row exactly: bare 403:, silent log. The block page only showed up when the request was made with curl.

The same thread also shows that ollama pull --insecure doesn't get around a proxy. It switches the registry requests to plain http://, and there it failed with connection reset by peer.

Find the blocked request

  1. Match your message to the table. A bare Error: 403: means a HEAD request. An HTML page after pull model manifest: 403: is the block page itself; read its title and policy text. context deadline exceeded plus failed to get direct URL warnings means the registry's blob URL. max retries exceeded: EOF plus attempt N failed: EOF lines means the download host.
  2. For the silent cases, make the same request with curl through the proxy the Ollama server uses and save what comes back, as in #19604. We have not run these commands against the real registry: 
    P="$HTTPS_PROXY"   # the value set for the Ollama *server* (e.g. in its systemd unit)
curl -sS -x "$P" -o /tmp/reg.txt -w '%{http_code} %{content_type}\n' https://registry.ollama.ai/v2/
curl -sS -x "$P" -o /tmp/manifest.txt -w '%{http_code} %{content_type}\n' \
  https://registry.ollama.ai/v2/library/llama3.2/manifests/latest
grep -io '<title>[^<]*' /tmp/reg.txt /tmp/manifest.txt
    A 403 with text/html is the proxy talking. A 401 with a JSON body means the proxy let you through to the registry, which wants a token (Ollama fetches the token itself). For the download host, ask whoever runs the proxy which host it refused for your machine: Ollama doesn't log that host name, and it changes per file.

Fixes

SituationWhat to do
The block page names a policy or categoryAsk for the registry and its download host to be allowed. Ollama v0.40.16's redirect check has special handling for cloudflarestorage.com, hf.co and huggingface.co hosts (see our redirect page), so the refused download host is likely under one of those; the proxy's own log will name it. Allowing only registry.ollama.ai leaves you with the max retries exceeded: EOF row.
curl works but Ollama gets 403The proxy settings must be in the server's environment (systemctl edit ollama.service, or the environment of ollama serve); the ollama pull command only talks to the local server. Also compare user agents and source accounts: a filter can treat Ollama's requests (user agents ollama/<version>, ollama-transfer/1.0 and Go's default in our logs) differently from curl's, or treat the service account differently from your own.
Hugging Face is allowed but Ollama's registry isn'tPull a GGUF from Hugging Face directly (ollama pull hf.co/<user>/<repo>), which was the way out in #8533.
Nothing can be unblocked in timePull on another network and copy the models folder (~/.ollama/models, or the folder in OLLAMA_MODELS) across, keeping its manifests/ and blobs/ layout.
Thinking about --insecureDon't. It switches to plain HTTP and skips address checks, and per #19604 it doesn't get past a proxy anyway.

Self-hosted registry: "Error: http: no Location header in response"

Our test caught one more message by accident. Our first stand-in registry served blob bytes straight back with 200 OK, the way a plain Docker/OCI registry or a simple mirror does, and Ollama v0.40.16 failed at once with:

Error: http: no Location header in response

The reason is the blob GET in blobDownload.run. It follows redirects only within the registry's own scheme, host and port, then takes the download address from the last response's Location header, even when that response is a 200. A registry that serves the bytes itself has no Location, so the pull stops there. With the same registry answering 307 to a second host, the pull succeeded. This matches #7244 (pulling from a local Docker registry, open since October 2024) and weightkeep PR #14 (September 2026), whose author fixed their Ollama-compatible server by answering blob GETs with 200 plus a Location header. A same-host 307 was not enough, because Ollama follows that and then still needs a Location on the final answer.

So a registry or mirror for Ollama has to answer blob GETs with a redirect to another host or port, or with a Location header. That target must also pass Ollama's redirect checks (see "redirect target not allowed"); our local test only passed because it used --insecure.

How this was made, and its limits

AI agents working for MV2 of Munim, Inc. built a small Python registry stand-in and ran the official Ollama v0.40.16 Linux amd64 release binary (checksum verified) against it in a sealed container on 12 November 2026, with a fresh models folder and server for each case. Each case was run once through the CLI and once through /api/pull, and every request was logged. All traffic stayed on 127.0.0.1 over plain HTTP with --insecure. The model was a tiny two-file stand-in (blobs of 23 and 278 bytes), not a real model. Limits:

  • A real proxy usually sits in front of HTTPS. It can only send a 403 page if it inspects TLS with a certificate your machine trusts (as in #19604). Otherwise the same block shows up as a TLS or connection error, which this test doesn't cover.
  • Which request a real proxy blocks depends on its rules. We didn't test against registry.ollama.ai or its real download hosts, and we don't know whether the real registry answers HEAD itself or redirects it.
  • We tested one version, v0.40.16. Other versions may print other text.
  • For a file smaller than the block page, the download-host case could end differently (the page's bytes would fill the whole file). We didn't test that.
  • The curl commands above were not run.
