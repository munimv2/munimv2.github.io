MCP: "Redirect to … not followed; use that URL as the endpoint if it is the intended server"

By MV2 of Munim, Inc., with AI agents. Written on 12 November 2026 from the source of the MCP Python SDK (v2.3.0, v1.30.0 and v1.29.1) and the MCP TypeScript SDK (v2.4.0 and 1.32.2), their release notes, and the issues linked below. Nothing was run; see limits.

An MCP server that worked yesterday now fails on connect, or on one tool call, with something like:

mcp.shared.exceptions.MCPError: Redirect to https://mcp.example.com/mcp/ not followed; use that URL as the endpoint if it is the intended server

The server (or something in front of it) answered the client's POST with an HTTP redirect, and the client refused to follow it. Since September and October 2026 the official MCP SDKs follow a redirect only when it stays on the same origin and keeps the POST a POST; before that they followed redirects anywhere. So this often appears right after an upgrade, with no change on the server. Most of the time the message's advice is right: put the URL it shows into your config. Three cases below are exceptions where that URL is the wrong fix.

Which redirects are still followed

The Python SDK (1.30.0 and later, 2.2.0 and later) and the TypeScript SDK (1.32.0 and later, 2.3.0 and later, default redirectPolicy: 'same-origin') use the same rule. A redirect of an MCP request is followed only if all of these hold:

  1. The method stays the same. MCP messages are POSTs. A 301, 302 or 303 turns a POST into a body-less GET, so for a POST only 307 and 308 are followed. A return 301 https://… rule in nginx, or a redirect directive that defaults to 301 or 302, therefore breaks the connection even when it points to the same host. (The long-lived GET stream may follow any of the five redirect codes.)
  2. The origin stays the same: same scheme, host and port. The one exception is http://host/… to https://host/… when both use the default port. http://host:8000 to https://host:8443, example.com to www.example.com, and any https-to-http step are refused.
  3. No new user name or password (user:pass@) in the target URL.
  4. At most a few hops: the httpx client's max_redirects in Python, MAX_REDIRECTS = 5 in the TypeScript SDK.

The rule came in with Python SDK PR #3397 (v2.2.0) and its backport PR #3448 (v1.30.0), both released 7 September 2026, and in TypeScript SDK 1.32.0 and v2.3.0 on 2 October 2026. Following redirects to another host had sent the client's configured headers, and on 307/308 the request body, to that host. Before the change, Python's create_mcp_http_client() set follow_redirects=True with no origin check (read at v1.29.1), and the TypeScript release notes say redirects were left to fetch, which follows them anywhere.

Common causes and the fix for each

What the message showsUsual causeFix
Your URL with or without a trailing /, same hostA proxy rule or framework sends 301/302 for the slash (refused for a POST). Starlette's own slash redirect is a 307 and is followed if nothing else is wrong.Use the URL from the message, slash included.
Your URL with https:// instead of http://The proxy redirects all plain HTTP to HTTPS with 301 or 302. The origin step is allowed, the method change is not.Configure the https:// URL.
An http:// URL while you configured https:// (the "downgrade" text)The app behind a TLS-terminating proxy builds its own redirects (usually the trailing slash) with http://, because it doesn't trust the proxy's X-Forwarded-Proto. Uvicorn, for example, trusts forwarded headers only from --forwarded-allow-ips, which defaults to $FORWARDED_ALLOW_IPS or else just 127.0.0.1 and ::1, so a proxy in another container doesn't count.Use the exact https URL that needs no redirect, or make the app trust the proxy's forwarded headers.
Another host or port: www., a new domain, a load balancer, a different portThe service moved, or a gateway sends you on. Refused even with 307/308.If that host is the same service and you trust it, use it as the endpoint.

When the URL in the message is the wrong fix

1. A login page. If the target is an identity provider or a /login, /oauth2/start, /sso path, an auth gateway (an SSO proxy, Cloudflare Access, a corporate portal) wants a browser sign-in. Making that URL the endpoint can't work. The fix is credentials the gateway accepts from a program (a service token or header it documents), or connecting past the gateway.

2. The target is your own endpoint, unchanged (Modal and similar platforms). Modal answers any web request that runs longer than 150 seconds with an HTTP 303 to the same URL plus a query parameter for the result (Modal: Request timeouts). The SDK refuses the 303 because it would turn the POST into a GET, and since the message drops the query string, it reads like Redirect to https://you--app.modal.run/mcp not followed, your own URL. Per PolicyEngine/macro#236 (merged 11 November 2026), a 5.5-minute tool call on mcp 1.30 failed exactly this way, and following the 303 by hand would not help, because Modal rejects the GET with 400 modal-http: bad redirect method. The fix is a tool that answers within 150 seconds: start the work as a job and poll for its result, as that project did. If the redirect only appears on slow tool calls and never on connect, suspect this.

3. A proxy that is meant to refuse it. A gateway that only lets MCP traffic reach allowlisted hosts relies on this rule: a redirect from an allowed host to another one is refused. Per LiteLLM PR #50629 (open), its test case 9 gets MCPError: Redirect to http://…:8722/mcp not followed; … as a tool error for a 307 to a different port. There the error is the protection working; adding the target to the allowlist is a security decision, not a fix.

Can you switch it off?

ClientOpt-out
MCP Python SDK 1.30.0+ / 2.2.0+None. Requests are sent with follow_redirects=False and the SDK follows within the origin itself; the follow_redirects setting of an httpx/httpx2 client you pass in is not consulted (mcp/shared/_httpx_utils.py). You can only change the hop count (max_redirects). Per python-sdk#3504 (open, labelled question), people behind reverse proxies are asking for an allowlist; there was none in v2.3.0.
MCP TypeScript SDK 1.32.0+ / 2.3.0+redirectPolicy: 'follow' on StreamableHTTPClientTransport or SSEClientTransport restores the old behaviour (redirects left to fetch, any origin). It gives up the protection described above, so prefer the final URL. In browsers, a redirected request fails unless that option is set (1.32.0 release notes).
Apps built on them (OpenAI Agents SDK, Open WebUI, …)Whatever the app exposes; in Open WebUI 0.13.3 nothing. Use the final URL.

See the redirect yourself

This sends one MCP initialize POST without following redirects and prints the status code and where it points. Add an -H 'Authorization: Bearer …' if the server needs one. We have not run this command.

curl -sS -o /dev/null -w '%{http_code} -> %{redirect_url}\n' -X POST \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  --data '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' \
  https://mcp.example.com/mcp

200 -> with nothing after it: no redirect on connect (if the error comes only on some tool calls, see the Modal case). 307 or 308 to the same host: followed by the SDKs, so look further along the chain by running the command again on the target. Anything else: the URL after the arrow is what the SDK refused; check it against the tables above. The Open WebUI page has a Python version that runs inside the container.
