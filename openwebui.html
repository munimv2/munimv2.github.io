Open WebUI security advisories: is my version affected?

Update, 9 November 2026: the short answer is now update to 0.13.3, Open WebUI's newest release (8 November 2026). 0.13.1, released the same day, is the third release in a row whose notes say it contains security fixes (after 0.12.5 and 0.13.0) and strongly recommend updating every deployment as soon as possible; again the fixes are not listed, and Open WebUI says it will publish advisories for them once CVE IDs are assigned. 0.13.2 fixes chats that stayed stuck on a spinner with crypto.randomUUID is not a function when Open WebUI is opened over plain HTTP at a LAN or Docker address. 0.13.3 fixes copy buttons over plain HTTP, and DeepSeek thinking-mode chats with skills, knowledge or memories that failed with a missing reasoning error; per its notes that fix needs the connection's Provider set to llama.cpp, and connections left on Default are unchanged. Neither the 0.13.2 nor the 0.13.3 notes mention security fixes.

Open WebUI has published no new advisory since 18 October 2026, so read per version, 0.13.3 is clear of all 166 advisories it has published, and 0.12.2 is still the oldest release that is. Treat anything before 0.13.1 as needing the update.

Before you upgrade: the 0.13.1 notes say it changes the database schema. Back up the database and its data first, and if several Open WebUI instances share one database, update them all at the same time: rolling updates are not supported and will cause application failures.

Defaults that change in 0.13.1 (from its release notes; the retrieval defaults checked in config.py at v0.13.0 and v0.13.3): with native function calling, which is the default, files attached to a chat are no longer added to the conversation automatically. The model reads them with its file tools, so a model without tool support can't see them unless you turn on Preload files in its Capabilities. RAG_TOP_K and RAG_TOP_K_RERANKER now default to 10 instead of 3, and CHUNK_SIZE to 1024 instead of 1000, unless you saved your own values. Prompts that use knowledge get longer, which costs more if Open WebUI talks to a paid model API. The new chunk size applies to files processed from then on; existing knowledge keeps its chunks until it is reindexed. If you use automatic SSO redirect, 0.13.1 also fixes the state mismatch error after a session expires (see the mismatching_state page).

Defaults that changed in 0.13.0 (checked 6 November 2026 in Open WebUI's source at v0.12.5 and v0.13.0): if you turned on sub-agents (ENABLE_SUBAGENTS, off by default), their limits are gone unless you set them. In 0.12.5 they defaulted to 20 foreground and 20 background sub-agents at once, 30 tool-call rounds each and an output cap of 30000. In 0.13.0 SUBAGENTS_MAX_CONCURRENT, SUBAGENTS_MAX_ASYNC, SUBAGENTS_MAX_ITERATIONS and SUBAGENTS_MAX_OUTPUT are empty by default, which means no limit. If Open WebUI talks to a paid model API, that is a cost risk: set the four variables (the old values were 20, 20, 30 and 30000) and restart Open WebUI. Separately, one chat response may now run up to 1024 rounds of tool calls instead of 256; CHAT_RESPONSE_MAX_TOOL_CALL_ITERATIONS=256 restores the old cap.

On 12 October 2026, Open WebUI's September 2026 advisories (all fixed in 0.11.4) had no CVE IDs and were not in the GitHub Advisory Database or OSV.dev, so pip-audit, Dependabot and other scanners that read those databases could report 0.11.3 as clean. By 1 November 2026 all 26 had CVE IDs (see the 1 November note above). Most people run Open WebUI from the ghcr.io/open-webui/open-webui Docker image, which those scanners don't check at all.

Find your version: in Open WebUI, open Settings > About. Or open http://localhost:3000/api/version (use your own address and port). With Docker, docker ps --format "{{.Image}}" | grep open-webui shows the tag, but :main and :latest don't tell you the version, so use the About page. The check runs in your browser and nothing you type is sent anywhere.

The ones to care about

  • Any website can take a signed-in user's session token (0.7.0 up to 0.11.4): a message listener didn't check where messages came from, so any page a signed-in user visits could get their token. This applies when community sharing is on, which is the default (GHSA-vpq8-f445-hcq7, CVSS 8.1, no CVE ID).
  • Shared chats that steal tokens (before 0.11.4): a javascript: link in a shared chat's citation or in its markdown runs script when a viewer clicks it (GHSA-qpqv-xwg8-cqpj, high; GHSA-wf9m-46cp-c6h6).
  • Terminals (0.8.6 up to 0.11.4): regular users could reach the Terminals admin API through the terminal proxy, manage its policies and stop other users' terminals (GHSA-q46m-r89w-j74p, high).
  • Cookies sent to tool servers (0.6.27 up to 0.11.4): connections, tool servers and terminals in OAuth mode forwarded the user's whole cookie jar, session cookie included, to the destination (GHSA-gqfh-jxvw-74rp).
  • Signing in as someone else (0.6.41 up to 0.11.1, SQLite): wildcard characters in OAuth or SCIM subject lookups let a user sign in as another account (CVE-2026-87016, high).

What to do

  1. Update to 0.13.3. With Docker, pull the image again (docker pull ghcr.io/open-webui/open-webui:main, or a pinned :v0.13.3) and recreate the container, keeping your data volume. Back up the volume first. 0.12.0 runs a database migration, and a few behaviours changed: a ?q= link now only fills the message box instead of sending it, and Redis room channels are on by default.
  2. Turn on two-factor sign-in. 0.12.0 adds it (ENABLE_MFA). It's most useful for admin accounts on servers other people can reach.
  3. Check who can reach it. ss -tlnp | grep 3000 on Linux (or 8080 for a pip install). If you publish it with Docker, -p 127.0.0.1:3000:8080 keeps it local. For other machines, put a reverse proxy with TLS in front: Open WebUI behind nginx or Caddy has configs that also fix the usual WebSocket and streaming errors. On Linux, ports Docker publishes skip ufw and firewalld.
  4. Behind a proxy? Set FORWARDED_ALLOW_IPS to your proxy's address unless nothing but the proxy can reach Open WebUI. If you start it with open-webui serve (pip installs), versions before 0.12.0 ignored this setting and trusted forwarded headers from every connection.
  5. If an affected version was reachable by people you don't fully trust, sign everyone out by rotating WEBUI_SECRET_KEY, review users and API keys, and rotate the provider API keys stored in Open WebUI's connections.
