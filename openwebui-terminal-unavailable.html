Open WebUI: "Terminal unavailable: Terminal server '…' is unavailable" and the other terminal errors

By MV2 of Munim, Inc., with AI agents. Written on 12 November 2026 from the source of all 18 Open WebUI releases from v0.10.0 to v0.13.3 (a scan for every terminal message, with the functions that raise them) and the issues linked below. Nothing was run against a terminal; see limits.

You picked a terminal in the chat's Terminal menu, the file browser still lists its files, but every message ends with:

Terminal unavailable: Terminal server 'terminal1' is unavailable

Open WebUI could not prepare the terminal's tools for the model, at the moment you sent the message. Since v0.11.0, any error while it does that is turned into an HTTP 503 with Terminal unavailable: plus the error's own text (process_chat_payload in backend/open_webui/utils/middleware.py), so the chat gets no answer at all, not an answer without tools. The part after the colon tells you which step failed. The file browser keeps working because it uses other requests, as an Open WebUI maintainer put it in #33976: "The message appears when Open WebUI cannot load the terminal's tool list from the URL set in the connection, at the moment a message is sent. The file browser uses other calls, so it keeps working."

What comes after "Terminal unavailable:"

All of these are raised in get_terminal_tools() in backend/open_webui/utils/tools.py, in this order. The first one that applies is the one you see.

A non-200 reply that is not JSON, such as an HTML 404 page, ends up as an aiohttp error about decoding JSON with an unexpected mimetype instead of the status code.Read it as the answer the terminal URL gave: connection refused = wrong host or port as seen from the Open WebUI server; 401/403 = key; HTML or mimetype = wrong URL or path.

Terminal server '<id>' is not available for chat (or for automation)0.11.1 to 0.13.3The connection's context for chats (or automations) is set to Off. The Terminal Contexts docs list Shared, Per chat and Off for each.Set the chat (or automation) row to Shared or Per chat.

On 0.13.0 the picker still offered per-chat terminals in temporary chats (#33861); the fix, PR #33866, was merged on 7 November 2026, the day before 0.13.1 was released, and the docs now say the picker hides such a terminal in temporary chats.

Two look-alikes that are not this error

  • Working directory is unavailable. Check the terminal connection and path. (0.13.1 to 0.13.3, HTTP 400, in backend/open_webui/utils/terminals.py). The first message of a chat carries the folder the file browser has open, and the server asks the terminal to move there (POST /files/cwd). This is the text when the terminal gives no folder back. A dev build before 0.13.1 also showed it for every personal terminal (#33811); PR #33814 fixed that before the release, and in 0.13.1 to 0.13.3 the code skips terminals the server doesn't connect to itself. If you see it, the folder no longer exists on the terminal or the terminal stopped answering: open the file browser in an existing folder and send again.
  • A file card in an earlier reply that reads "Terminal unavailable" with Download and Open greyed out (in the page itself since 0.11.1). That card shows a file from a terminal that isn't picked now. Per #34101 (open, reproduced on 0.13.3), the card keeps saying so after you pick the terminal again, until you reload the page. Reload; nothing is wrong with the terminal.

Personal terminals on 0.11.x

On 0.11.0 (27 July 2026), picking a personal terminal made every chat fail with Terminal unavailable: Terminal server 'http://…' not found. Per the root cause posted in #27621, the page identified personal terminals by URL and admin ones by connection id, but sent either as terminal_id, and the server only looked it up among admin connections. Admin-configured terminals kept working. The maintainers fixed it on the dev branch and said it would ship in the next release (0.11.1 came out on 25 August 2026). In the source, 0.11.4 (21 September) added a second guard: the server only builds terminal tools for ids that are in your connection list.

From 0.11.4, a different error hit personal terminals: the server tried to load terminal skills from a terminal only your browser can reach, and the whole message failed with the connection error (for example Cannot connect to host localhost:8000 ssl:default [Connect call failed ('127.0.0.1', 8000)]). Per a maintainer in #30341, that is the same bug as #30410, fixed by PR #30423; until then, turning the terminal off for the chat avoided it.

Test the terminal URL the way Open WebUI does

Run this inside the Open WebUI container (for example docker exec -it open-webui sh), with the URL exactly as entered in the connection. It is the check a maintainer asked for in #33976. We have not run these commands.

curl -s -o /dev/null -w '%{http_code}\n' http://open-terminal:8000/openapi.json
# with a key (Bearer or, on 0.13.1+, Session connections):
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: Bearer YOUR_KEY' http://open-terminal:8000/openapi.json
# orchestrator connections use the policy path:
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: Bearer YOUR_KEY' http://orchestrator:8080/p/POLICY_ID/openapi.json

If the image has no curl, Python is always there:

python3 -c "import urllib.request as u,sys; r=u.urlopen(u.Request(sys.argv[1], headers={'Authorization':'Bearer '+sys.argv[2]}), timeout=10); print(r.status, r.headers.get('content-type'))" http://open-terminal:8000/openapi.json YOUR_KEY

200 with JSON: the URL is fine, so look at the connection's key, contexts and access settings, and reload the page. 000 or a connection error: the server can't reach that address (see the localhost row above). 401/403: key or auth mode. 404 or HTML: wrong URL or path. Then send a message and read the server log lines just before the 503: Could not fetch tool server spec, Failed to connect to and Invalid OpenAPI spec are the ones the maintainer named.

When you report it, the maintainers ask for: where the terminal is configured (Admin Settings > Integrations, your personal Integrations, or TERMINAL_SERVER_CONNECTIONS) with the key removed; whether Open WebUI and the terminal share a Docker network, and the URL; whether you run Redis or more than one Open WebUI instance; the log lines; and the probe's output (all from #33976).
