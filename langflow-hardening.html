Langflow has no login? Turn off auto-login, and the other defaults to change

Update, 2 November 2026: Langflow 1.13.0 (22 October 2026) turns automatic login off by default. In Langflow's settings code, AUTO_LOGIN defaults to True in 1.12.8 and to False in 1.13.0 (pull request #14993). With it off, Langflow stops at startup until LANGFLOW_SUPERUSER_PASSWORD is set, and it refuses the old default password. This page was written for 1.12.x. Steps 2 and 3 still apply to older releases and to anyone who sets LANGFLOW_AUTO_LOGIN=true.

Upgrading an install that used auto-login? Keep the same account. Your flows belong to the account auto-login signed you in as (langflow, unless you set LANGFLOW_SUPERUSER). Langflow's upgrade guide warns that creating a different superuser, like the administrator example in step 3, does not move those flows to it. Set a password on the existing account before you upgrade, or see Langflow won't start: "Username and password must be set" if you already upgraded.

The newest release when checked on 2 November 2026 is 1.13.0 (22 October 2026). It is clear of all 35 advisories Langflow has published for the langflow package (the newest on 28 September 2026), so the steps below now name 1.13.0 instead of 1.12.5. Step 8's SSRF advice still holds in 1.13.0: SSRF protection is on, LANGFLOW_CONNECTOR_SSRF_ALLOW_LOOPBACK still defaults to True and LANGFLOW_SSRF_ALLOWED_HOSTS is still empty by default.

By MV2 of Munim, Inc., with AI agents. Checked against Langflow's API keys and authentication and environment variables docs (version 1.12.x), Langflow's source (api/v1/login.py) and its security advisories on 12 October 2026, with 1.12.5 the latest release. For your own servers only.

If you installed Langflow with pip or uv and ran langflow run, it never asked you for a password. That's auto-login: Langflow's docs say it "automatically signs in all users as the configured superuser". That's fine on a laptop that nobody else can reach. On a server, a shared machine or a forwarded port, it means anyone who can open the page is the admin, and in Langflow the admin can run Python on the host. This page goes through the settings to change, in order. To check your version against known flaws, use the Langflow advisories page.

The short answer

  • Update first. Before 1.10.3 a signed-in user, and with auto-login anyone, can run OS commands through MCP server settings (GHSA-w794-rj3p-xv45, critical). Go to 1.13.0.
  • LANGFLOW_AUTO_LOGIN defaults to True for pip installs before 1.13.0. From 1.13.0 it defaults to False, and Langflow will not start until LANGFLOW_SUPERUSER_PASSWORD is set (what to do). Langflow's docs add that "official Langflow Docker images set false", so a Docker install usually already has a login. Set it to False with your own superuser name and password.
  • CORS is open by default: origins * with credentials allowed. Langflow's docs warn that this means "any website can make requests to your Langflow API". Set LANGFLOW_CORS_ORIGINS to the address you use.
  • Don't swap LANGFLOW_SECRET_KEY on an install that already stores credentials. Langflow encrypts stored API keys with it. Changing it needs the migration script from Langflow's SECURITY.md.
  • Keep port 7860 on 127.0.0.1 and reach it over a VPN or an HTTPS proxy. Langflow's docs: "Never expose Langflow ports directly to the internet without proper security measures."

1. Update

Find your version at http://127.0.0.1:7860/api/v1/version or with pip show langflow, and type it into the CVE checker. The critical 2026 advisories are fixed by 1.10.3; 1.12.0 also removes an eval() in tool-mode inputs (GHSA-33p4-w7j3-33mw). In Docker, pin a release tag you've tested, such as langflowai/langflow:1.13.0, rather than latest.

2. Is auto-login on? One request tells you

The Langflow editor calls /api/v1/auto_login when it loads. In Langflow's source, that endpoint returns a superuser access token when auto-login is on, and 403 with "Auto login is disabled." when it's off. On the Langflow machine:

curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:7860/api/v1/auto_login
# 403 = auto-login is off: people have to sign in
# 200 = anyone who can reach this port is signed in as superuser

A 200 on a laptop that only you use is expected. On anything other people or other machines can reach, go on to step 3.

3. Turn auto-login off

Put the settings in an .env file next to Langflow, readable only by you (chmod 600 .env). These are the values from Langflow's own production example, plus the CORS and cookie settings from steps 5 and 6:

LANGFLOW_AUTO_LOGIN=False
LANGFLOW_SUPERUSER=administrator
LANGFLOW_SUPERUSER_PASSWORD=change-me-to-a-long-random-password
LANGFLOW_NEW_USER_IS_ACTIVE=False
LANGFLOW_ENABLE_SIGNUP=False
LANGFLOW_ENABLE_SUPERUSER_CLI=False
# only if you serve Langflow at this HTTPS address (steps 5 and 6):
LANGFLOW_CORS_ORIGINS=["https://langflow.example.com"]
LANGFLOW_ACCESS_SECURE=True
LANGFLOW_REFRESH_SECURE=True

Then start it with uv run langflow run --env-file .env (or langflow run --env-file .env). What each line does, from Langflow's docs:

  • LANGFLOW_SUPERUSER_PASSWORD is required once auto-login is off. It "can't use the legacy default value langflow; startup fails closed instead". Generate one with python3 -c "import secrets; print(secrets.token_urlsafe(24))".
  • LANGFLOW_NEW_USER_IS_ACTIVE=False (the default) keeps new accounts "inactive until a superuser activates them". LANGFLOW_ENABLE_SIGNUP=False stops people creating accounts at all. Add users yourself instead.
  • LANGFLOW_ENABLE_SUPERUSER_CLI=False: the default is true, but the docs recommend false "to prevent unrestricted superuser creation".

Before you switch, export your flows as JSON from the editor. Flows made under auto-login belong to the auto-login account. If they don't show up under the account you sign in with afterwards, import them again.

Docker: the official images already set auto-login off, so the image needs a superuser password at start. A Compose file that keeps the port on this machine:

services:
  langflow:
    image: langflowai/langflow:1.13.0
    env_file: .env
    ports:
      - "127.0.0.1:7860:7860"   # not "7860:7860": on Linux, Docker-published ports skip ufw
    volumes:
      - langflow-data:/app/langflow
volumes:
  langflow-data:

4. LANGFLOW_SECRET_KEY: set it on a new install, keep it on an old one

Langflow encrypts sensitive data, such as the API keys you save as global variables, with this key, and signs login tokens with it. If you don't set one, "Langflow automatically generates one" and keeps it.

  • New install: set it before you save any credential. Generate it the way the docs do: python3 -c "from secrets import token_urlsafe; print(token_urlsafe(32))", and add LANGFLOW_SECRET_KEY=... to .env.
  • Existing install: don't paste in a new key. Stored credentials were encrypted with the old one. To rotate it, use the migration script that "re-encrypts stored credentials and other sensitive data with a new key", described in Langflow's SECURITY.md. Back up the database first.
  • Back the key up with the database. More than one Langflow instance has to share the same key.
  • Before 1.10.1 a short secret key made the encryption key weak (GHSA-jxw3-mjmx-3pqm). Another reason to update.

5. CORS: name your own address

The defaults are LANGFLOW_CORS_ORIGINS=* with LANGFLOW_CORS_ALLOW_CREDENTIALS=True and all headers and methods. Set the origins to the exact address in your browser's address bar. That's https://langflow.example.com, with no trailing slash, as a JSON list as in step 3. If you only use Langflow at http://localhost:7860, the editor talks to its own origin, so LANGFLOW_CORS_ORIGINS=["http://localhost:7860"] works too. Check it:

curl -s -D - -o /dev/null -H "Origin: https://example.org" http://127.0.0.1:7860/api/v1/version | grep -i access-control-allow-origin
# no output = other websites are refused. "*" or "https://example.org" = still open

6. Cookies over HTTPS

The access and refresh cookies are HttpOnly by default, but not Secure. If you reach Langflow over HTTPS, set LANGFLOW_ACCESS_SECURE=True and LANGFLOW_REFRESH_SECURE=True, as the docs say. The default SameSite=lax is right for one address. Only a deployment where the editor and API are on different sites needs LANGFLOW_REFRESH_SAME_SITE=none.

7. API keys

  • Per the docs, most API endpoints, such as /api/v1/run/<flow id>, require a Langflow API key in an x-api-key header. Create one per app in Settings → Langflow API Keys, and revoke keys you no longer use.
  • Don't set LANGFLOW_SKIP_AUTH_AUTO_LOGIN=true. With auto-login on, it lets API requests skip the key check. The docs say it "will be removed in a future release".
  • LANGFLOW_API_KEY_SOURCE=env checks one key from the environment, and "successful authentication grants superuser privileges". Use the default, db, unless you need that.
  • Keep LANGFLOW_WEBHOOK_AUTH_ENABLE at its default, True. With False, "all requests to the webhook endpoint are treated as being sent by the flow owner".

8. Code execution: decide who may run Python

Langflow lets users edit a component's Python code in the editor, and that code runs on the server. So treat every account that can build flows as an account that can run code on the host. If other people use your Langflow:

  • LANGFLOW_ALLOW_CUSTOM_COMPONENTS=False turns off custom components and in-editor code editing, and blocks the built-in code-execution components at run time. The docs mark it beta, so test your flows after setting it.
  • LANGFLOW_BLOCK_CODE_INTERPRETER_COMPONENTS=True blocks just the built-in code-execution components. LANGFLOW_RESTRICT_LOCAL_FILE_ACCESS=True keeps file components inside the upload folder.
  • Need user code anyway? LANGFLOW_SANDBOX_BACKEND=exec-sandbox runs it in a separate QEMU microVM per execution.
  • MCP: a stdio MCP server is a command Langflow starts on the host. LANGFLOW_MCP_SERVER_DOCKER_HARDENING=True applies a strict policy to Docker-based ones, and leaving LANGFLOW_MCP_SERVER_ENV_ALLOWLIST empty blocks user-supplied environment variables.
  • SSRF: the protections are on by default, but LANGFLOW_CONNECTOR_SSRF_ALLOW_LOOPBACK defaults to True. On a shared server, set it to False and allow only the internal hosts your flows need with LANGFLOW_SSRF_ALLOWED_HOSTS (for example 10.0.0.5,*.internal.example.com). Otherwise a flow can call other services on the same machine, such as an Ollama with no key.

9. Keep port 7860 private

langflow run listens on localhost by default (LANGFLOW_HOST). Don't change that to 0.0.0.0 to reach it from another machine. Use one of these instead:

  • Over a VPN or Tailscale: keep Langflow on localhost and use tailscale serve or an SSH tunnel (ssh -L 7860:127.0.0.1:7860 you@server). The remote access page explains both for Ollama. Use port 7860 instead of 11434.
  • An HTTPS proxy, with the cookie settings from step 6. Caddy: 
    langflow.example.com {
    reverse_proxy 127.0.0.1:7860 {
        flush_interval -1
    }
}
    flush_interval -1 passes streamed output through as it arrives. If only your team needs the editor, add a remote_ip rule as in the LiteLLM page, and let only /api/v1/run/* and /api/v1/webhook/* through from outside.

10. Test it

# auto-login off: should print 403
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:7860/api/v1/auto_login

# running a flow without a key: should NOT print 200
curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "Content-Type: application/json" \
  -d '{"input_value":"hi"}' http://127.0.0.1:7860/api/v1/run/YOUR_FLOW_ID

# from ANOTHER machine, straight to Langflow: should fail to connect
curl --max-time 5 http://<server LAN IP>:7860/api/v1/version

If the last one answers, port 7860 is open to the network. Check LANGFLOW_HOST and Docker's ports:, and on Linux run ss -tlnp | grep 7860 (it should show 127.0.0.1:7860). Mistakes to avoid

  • Publishing -p 7860:7860 or setting LANGFLOW_HOST=0.0.0.0 on a machine with auto-login on.
  • Pasting a new LANGFLOW_SECRET_KEY into an install that already stores credentials, or losing the old one.
  • Leaving CORS at * on a server you sign in to from your browser.
  • Setting LANGFLOW_SKIP_AUTH_AUTO_LOGIN=true or LANGFLOW_WEBHOOK_AUTH_ENABLE=False to make an error go away.
  • Handing out one LANGFLOW_API_KEY_SOURCE=env key: everyone who has it is superuser.
  • Treating a login as enough for untrusted users. Signed-in users can still run code unless you apply step 8.
