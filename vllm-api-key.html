vLLM --api-key doesn't cover every endpoint. Here's how to lock vLLM down

By MV2 of Munim, Inc., with AI agents. Checked against vLLM's security guide, the vllm serve reference, the Docker guide, vLLM's server launcher source and the Caddy matcher docs on 12 October 2026, with vLLM 0.31.0 the latest release. For your own servers only.

The short answer

  • --api-key only checks some routes. vLLM's security guide says it applies "only for endpoints under the /v1, /v2, /inference, and /cohere path prefixes", and that "many other sensitive endpoints are exposed on the same HTTP server without any authentication enforcement." Its advice: "Do not rely exclusively on --api-key for securing access to vLLM."
  • What stays open without a key, per that guide: /invocations (the same inference as /v1), /pooling, /classify, /score, /rerank, /tokenize, /detokenize, and operational routes such as /pause, /resume, /abort_requests and /update_weights. Anyone who can reach the port can run prompts on your GPU, pause the server or cancel other people's requests.
  • vllm serve listens on every interface by default. If you don't pass --host, the launcher binds to "", which is all interfaces, and reports http://0.0.0.0:8000. Docker's -p 8000:8000 does the same on the host.
  • The fix: bind vLLM to 127.0.0.1 (or keep it on a private Docker network), and put a reverse proxy in front that passes only the endpoints your apps use, with a key, and answers everything else with 404. That's what vLLM's guide calls "the most effective approach".

If only programs on the same machine use vLLM, step 1 alone is enough: bind it to 127.0.0.1 and check with the tests in step 4.

1. Bind vLLM to localhost and set a key

Generate a long random key with openssl rand -hex 32. Pass it through the VLLM_API_KEY environment variable rather than --api-key on the command line, where every user on the machine can read it in the process list. Keep the key in vLLM as well as in the proxy, so a mistake in one layer doesn't leave the /v1 routes open.

export VLLM_API_KEY='PASTE_YOUR_KEY_HERE'
vllm serve Qwen/Qwen3-8B --host 127.0.0.1 --port 8000 --disable-fastapi-docs

--disable-fastapi-docs removes the Swagger UI and OpenAPI schema, which list every route. Don't set VLLM_SERVER_DEV_MODE=1 on a server others can reach: it adds /collective_rpc, which the guide calls "extremely dangerous", along with /sleep and cache-reset routes. Leave the profiler and --enable-tokenizer-info-endpoint off too.

With Docker

Give the vllm service no ports: and publish only the proxy. If you use plain docker run, publish with -p 127.0.0.1:8000:8000 instead of -p 8000:8000; on Linux, ports Docker publishes skip ufw and firewalld rules.

services:
  vllm:
    image: vllm/vllm-openai:v0.31.0
    command: [ "--model", "Qwen/Qwen3-8B", "--disable-fastapi-docs" ]
    environment:
      - VLLM_API_KEY=${VLLM_API_KEY}
      - HF_TOKEN=${HF_TOKEN}
    ipc: host
    volumes: [ "~/.cache/huggingface:/root/.cache/huggingface" ]
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [ gpu ]
    # no "ports:" - only containers on this network can reach vLLM
  caddy:
    image: caddy:2
    ports: [ "80:80", "443:443" ]
    volumes: [ "./Caddyfile:/etc/caddy/Caddyfile:ro", "caddy_data:/data" ]
volumes:
  caddy_data: {}

Put VLLM_API_KEY=... in a .env file next to the compose file (readable only by you), and use reverse_proxy vllm:8000 in the Caddyfile below.

2. Caddy: allow only what your apps call

Most OpenAI-style clients need just these four routes. Replace the domain and PASTE_YOUR_KEY_HERE; Caddy gets an HTTPS certificate on its own when the domain points at this machine.

llm.example.com {
    @api path /v1/chat/completions /v1/completions /v1/embeddings /v1/models
    @api_with_key {
        path /v1/chat/completions /v1/completions /v1/embeddings /v1/models
        header Authorization "Bearer PASTE_YOUR_KEY_HERE"
    }

    handle @api_with_key {
        reverse_proxy 127.0.0.1:8000 {
            flush_interval -1
        }
    }
    handle @api {
        respond "Missing or wrong API key" 401
    }
    handle {
        respond 404
    }
}
  • Inside one named matcher, different matcher types must all match, so @api_with_key needs an allowed path and the exact Bearer header. Caddy keeps handle blocks with named matchers in the order written and runs only the first that matches; the block with no matcher runs last.
  • The path matcher is an exact match, so /invocations, /tokenize, /pause, /metrics and everything else gets 404. Add a route only when an app needs it, for example /v1/responses or /v1/rerank (the /v1/ form is the one --api-key also checks).
  • flush_interval -1 sends streamed tokens as they arrive.
  • Several keys: add one more header Authorization "Bearer ..." line per key inside @api_with_key; Caddy ORs values of the same header. vLLM's own --api-key check then has to accept them too, so either give vLLM the same keys or remove the Authorization header in the proxy (header_up -Authorization) and rely on the proxy plus the localhost bind.
  • The Caddyfile now holds a secret: sudo chown root:caddy /etc/caddy/Caddyfile && sudo chmod 640 /etc/caddy/Caddyfile && sudo systemctl reload caddy

3. Or nginx

Put this in /etc/nginx/conf.d/vllm.conf (files there are read inside the http block, where map belongs) and use your own certificate paths:

map $http_authorization $vllm_key_ok {
    default                        0;
    "Bearer PASTE_YOUR_KEY_HERE"   1;
}

server {
    listen 443 ssl;
    server_name llm.example.com;
    ssl_certificate     /etc/letsencrypt/live/llm.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/llm.example.com/privkey.pem;

    location ~ ^/v1/(chat/completions|completions|embeddings|models)$ {
        if ($vllm_key_ok = 0) { return 401; }
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_buffering off;          # stream tokens as they come
        proxy_read_timeout 600s;      # long generations
    }

    location / {
        return 404;                   # /invocations, /tokenize, /pause, /docs ...
    }
}

Run sudo nginx -t && sudo systemctl reload nginx and make the file readable only by root (sudo chmod 600 /etc/nginx/conf.d/vllm.conf). nginx sends its own Host header upstream, which is also why vLLM's guidance for CVE-2026-48746 (a crafted Host header skipped the key check before 0.22.0) says servers behind such a proxy weren't affected.

4. Test it

# no key: should print 401
curl -s -o /dev/null -w "%{http_code}\n" https://llm.example.com/v1/models

# with the key: should list your model
curl -H "Authorization: Bearer YOUR_KEY" https://llm.example.com/v1/models

# routes --api-key doesn't cover: should print 404
curl -s -o /dev/null -w "%{http_code}\n" -X POST https://llm.example.com/invocations
curl -s -o /dev/null -w "%{http_code}\n" -X POST https://llm.example.com/pause

# from ANOTHER machine, straight to vLLM: should fail to connect
curl --max-time 5 http://<server LAN IP>:8000/version

If the last command prints a version, vLLM can be reached without the proxy: check --host, Docker ports:, and on Linux ss -tlnp | grep 8000 (it should show 127.0.0.1:8000, not 0.0.0.0:8000 or *:8000).

5. Multi-GPU, multi-node and disaggregated setups

The proxy protects the HTTP API only. vLLM's guide says traffic between nodes is "insecure by default": PyTorch distributed, KV-cache transfer and the parallelism channels are unencrypted and unauthenticated, and PyTorch's TCPStore "by default, listens on all network interfaces."

  • Run the nodes on an isolated network, and on each node block incoming connections except the API server's port (and only from the proxy).
  • Set VLLM_HOST_IP to the node's private address rather than leaving it to the default.
  • If you use the gRPC server (--grpc-port), it binds to the same address as the HTTP server and the guide calls it "insecure by default"; keep it off public interfaces.
  • Disaggregated serving with P2pNcclConnector from 0.9.2 up to 0.24.0: a request's X-Request-Id header could make the server connect out and leak KV-cache data, that is, other users' prompts (GHSA-vfp2-c8pq-v6h6). Update; the proxy above doesn't remove that header.
  • Several tenants sharing one server: give each a cache_salt so prefix-cache hits can't be used to learn what others sent, and limit which media URLs the server fetches with --allowed-media-domains.

Mistakes to avoid

  • Proxying / to vLLM with a key check. It's better than nothing, but it still passes /pause, /update_weights and the rest to anyone holding the key. Allow only named routes.
  • The proxy is in place, but port 8000 is still open. Run the last test above from another machine.
  • Treating the proxy as the whole fix. Anyone with the key still reaches the inference code that most of this year's vLLM advisories are in, several with no CVE ID and missing from OSV. Update to 0.31.0 (see vLLM advisories, or type your version into the CVE checker).
  • Using /health for a load balancer through the public proxy. Point health checks at 127.0.0.1:8000/health on the host, or add only /health to the allowed paths without a key; it reveals little.

Running Ollama instead? The same idea for Ollama, which has no key at all: Ollama API key.
