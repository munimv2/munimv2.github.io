Open WebUI SSO: "mismatching_state: CSRF Warning! State not equal in request and response"

By MV2 of Munim, Inc., with AI agents. Checked on 7 November 2026 against the source of Open WebUI 0.13.0, the newest release then. Every cause below was run with the libraries that release pins (Authlib 1.7.2, FastAPI 0.136.3, Starlette 1.10.0) and Open WebUI's own session settings, against a small local identity provider, not a full Open WebUI install.

After you sign in at your identity provider (Keycloak, Authentik, Entra ID, Google, and so on), Open WebUI sends you back to its sign-in page with this message:

Sign-in with your identity provider failed. Please contact your administrator for assistance.

The reason is in the server log (docker logs open-webui), in a warning like this:

OAuth callback error during authorize_access_token for provider oidc: OAuth callback failed: mismatching_state: CSRF Warning! State not equal in request and response.

Short answer: the redirect back from the provider arrived without the browser session that started the sign-in, or with a session that no longer holds that sign-in. When you click the SSO button, Open WebUI stores a one-time state in its owui-session cookie, signed with WEBUI_SECRET_KEY (or in Redis, if ENABLE_STAR_SESSIONS_MIDDLEWARE=true and REDIS_URL are set). When the provider sends you back, Authlib compares the state in the URL with the one in that session. If the cookie is missing, was signed with another key, or no longer holds that state, you get this error. Open WebUI's issue #33783 (opened 5 November 2026) describes one way this happens with automatic SSO redirect after a sign-in token expires; it was closed as completed on 6 November 2026, after Open WebUI 0.13.0 was released, so look for the fix in a later release.

Open WebUI's own SSO troubleshooting page lists this error too. This page adds a run of each cause, so you can tell them apart.

In every mismatching_state row, Authlib raised mismatching_state: CSRF Warning! State not equal in request and response. at the callback; Open WebUI logs that and redirects to /auth?error=… with the message above.

Which one is it? Look at the callback request

  1. Open the browser's developer tools (F12), Network tab, and tick "Preserve log".
  2. Click the SSO button and sign in at the provider.
  3. Find the request to /oauth/<provider>/login/callback (or the older /oauth/<provider>/callback) and look at its request headers.
  • No owui-session in its Cookie header: the browser didn't send the cookie. Compare the callback's address with the address you opened Open WebUI at (scheme, host, port), then check WEBUI_SESSION_COOKIE_SAME_SITE and WEBUI_SESSION_COOKIE_SECURE.
  • owui-session is there: the cookie arrived but didn't hold the state. Usually another replica with a different secret key handled it, sign-in was started again in another tab, or the callback was loaded a second time.

Set one WEBUI_SECRET_KEY for every container

If you never set WEBUI_SECRET_KEY, Open WebUI's start.sh generates one into /app/backend/.webui_secret_key inside the container. The docker run commands in Open WebUI's README mount the volume at -v open-webui:/app/backend/data, so that file is not in it: each replica, and each new container (for example after docker pull and re-create), makes its own key. Check whether yours is set:

docker exec open-webui sh -c 'if [ -n "$WEBUI_SECRET_KEY" ]; then echo set; else echo "not set: generated in /app/backend/.webui_secret_key"; fi'

Generate one value once (openssl rand -hex 32), keep it with your other secrets, and pass the same value to every container, for example -e WEBUI_SECRET_KEY=… in docker run or under environment: in Docker Compose.
